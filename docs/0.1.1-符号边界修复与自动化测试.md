# 0.1.1：符号边界修复与自动化测试

交付日期：2026-09-07。插件名 `contextualPronunciation`，版本 `0.1.1`，最低/已测试 NVDA 版本均为 `2026.2`。这是对 0.1.0 的兼容修复，不改变设置键，不要求删除已有用户规则。

## 1. 根因与修复范围

用户反馈“盛汤”后加竖线、美元符号、脱字符、加号、等号、小于号、大于号、反引号、波浪号，纠正失效。旧代码下逐项复现，9 项全部失败；原始记录见 `artifacts/boundary-before-fix.log`。

原因在插件的公共 `_is_boundary`，不在 VE 收到纠正后文本的合成环节。旧代码只接纳 Unicode 的 P（标点）、Z（分隔符）以及 `isspace()`，没有接纳 S（符号）。Unicode 对这几类有明确定义，并不把所有键盘“标点符号”都归为 P。[Unicode UAX #44](https://www.unicode.org/reports/tr44/#General_Category_Values)

| Unicode 类别 | 本次失败字符或扩展实例 | 原判定 |
|---|---|---|
| Sm，数学符号 | 竖线、加号、等号、小于号、大于号、波浪号 | 漏判 |
| Sc，货币符号 | 美元符号；同类还有人民币符号、欧元符号 | 漏判 |
| Sk，修饰符号 | 脱字符、反引号 | 漏判 |
| So，其他符号 | 星形、许多表情图符 | 同类风险 |

“盛汤、盛饭、盛水”等规则特意要求右边界，以避免误改“盛汤姆、盛饭店、盛水准”。因此旧版看到“盛汤$”时不承认“汤”后的词组结束位置，原文“盛”继续进入 VE，恢复为引擎原来的 shèng。

修复后的判定是 `isspace()` 或 Unicode 类别首字母属于 `P/S/Z`。这是本插件的局部发音规则分隔约定，不是通用中文分词或 Unicode 单词切分算法。

同一个判定被词组左右边界、`rowOrdinal`、`rowCount`、`rankOrder`、`rowLabel` 共用。本次修的是这个公共契约，没有给 9 个字符逐一加白名单，也没有取消词组保护条件。全角变体、其他货币符号、数学符号及其他 S 类字符随之覆盖。

依旧保守处理的情况：汉字、拉丁字母、数字、组合附加符、变体选择符、非空白控制/格式字符、私用/未指派码位不一概当边界；不删除它们，也不跳过它们向后猜测。因此“盛汤”后紧接这类字符不在本次“全部可见符号”修复承诺内。未知上下文仍可能由引擎决定。

## 2. 语音链路与安全

应用文本 → 插件公开 `filter_speechSequence` → NVDA 发音词典 → NVDA 符号处理 → 合成器。

例如“盛汤$”在插件阶段变成临时语音文本“成汤$”，之后由 NVDA 按用户当前符号级别决定是否报告美元符号。插件不删除 `$`，不强制更改符号级别，不修改文档、剪贴板或盲文，不插入 VE 私有命令。

这一顺序已用固定 NVDA 提交的真实 `speech.speech.speak` 验证，而不只检查替换函数。参见[固定版本的 NVDA 语音实现](https://github.com/nvaccess/nvda/blob/f62c980589d1ac30babf68ad48177e9ad29a2e84/source/speech/speech.py)。用户字典在插件之后执行，仍可能主动覆盖临时同音字；已有 `keep`/禁用规则功能保留。

生产运行代码只有公共边界实现及版本/帮助更新；没有引入运行期网络、分词模型、新线程、正则扫描、发音缓存或额外 I/O。算法每次检查边界仍只访问邻接的一个码点并查询一次 Unicode 类别，时间复杂度不变。

## 4. 本机原生编译实际完成了什么

NVDA 源码固定为 `f62c980589d1ac30babf68ad48177e9ad29a2e84`，依赖子模块递归固定到该提交引用的版本；没有修改上游源码。遵循 NVDA 官方的 `scons source` 和 `rununittests.bat` 路线。[开发环境要求](https://github.com/nvaccess/nvda/blob/f62c980589d1ac30babf68ad48177e9ad29a2e84/projectDocs/dev/createDevEnvironment.md)、[源码构建说明](https://github.com/nvaccess/nvda/blob/f62c980589d1ac30babf68ad48177e9ad29a2e84/projectDocs/dev/buildingNVDA.md)、[自动化测试说明](https://github.com/nvaccess/nvda/blob/f62c980589d1ac30babf68ad48177e9ad29a2e84/projectDocs/testing/automated.md)

本机使用 Visual Studio Community 2026 18.8.3、MSVC 14.51.36231、Windows SDK 10.0.26100.0、NVDA 固定的 Python 3.13.13 和 SCons 4.10.1。插件独立测试/基准另在系统 Python 3.13.5 上执行。

初次构建遇到并处理了两个真实环境问题：

1. 机器有 clang-format/clang-tidy，却没有 clang-cl。下载官方 LLVM 20.1.8 Windows 发布资产，校验 SHA-256 后，仅用 7-Zip 提取到 `vendor/llvm-20.1.8`，未执行安装程序。没有改注册表或全局 PATH。[LLVM 官方发布页](https://github.com/llvm/llvm-project/releases/tag/llvmorg-20.1.8)
2. ARM64 的非 Spectre ATL 目录缺少 `atls.lib`，但同一 MSVC 工具集的 Spectre 目录已有。显式启用开发脚本中的后备目录选择，编译/链接实际成功；未跨工具集或架构替换库，未关闭编译错误检查。

SCons 不自动继承调用者 PATH，因此 `scripts/nvda_scons/site_init.py` 只在显式选择本地 LLVM 时提供构建环境适配。它不是插件生产代码，不会进入 `.nvda-addon`，也不改变 NVDA 的发音代码。使用本机上述环境重新执行 `scons source` 已成功；x86/x64/ARM64/ARM64EC 构建产物哈希记录在工作流报告中。

这里完成的是 `source` 构建目标和本机 x64 上的测试，不是打包 NVDA launcher，也不等于在 ARM 设备上执行测试。

原生链路测试采用 NVDA 自带的隔离测试配置；替身仅用于安装位置相关的翻译发现、当前声音身份/语言，以及合成器出口的捕获。没有将测试配置写回 `%APPDATA%\nvda`。没有执行 `runnvda.bat`、Robot 桌面系统测试或重启正在运行的 NVDA。

最终复核时，官方 `Test_ScreenCurtain.test_setAndConfirmBlackFullscreenColorEffect` 检测到已有外部全屏颜色效果，按上游代码跳过；工作流未为重测而关闭/复位这一效果。`--allow-external-screen-effect` 是显式记录这个确切环境例外的选项，不把 skip 改成 pass，不接受其他跳过或理由。官方套件包含调用 Windows 显示/鼠标 API 的测试，并非全部纯内存测试；严格隔离桌面副作用时应在专用 Windows 虚拟机运行。原生发音链路的 4 项测试和插件的 96 项测试均不使用此例外。

## 5. 一键复现

日常开发需要 Python 3.13、Git、uv。完整工作流另需 Visual Studio C++/SDK/Clang，以及运行声学门禁时本机合法安装的 Vocalizer Expressive 2 与 Ting-Ting。工作流静态检查使用固定版本 actionlint 1.7.12 官方 Windows 发布包，先校验 SHA-256 再缓存到 `vendor/actionlint-1.7.12`；再次运行复核缓存，无需 Go 环境或反复访问 Go 下载代理。

只跑插件测试与打包：

```powershell
python scripts/prepare_nvda.py
.\build.ps1
```

本机已准备好独立 LLVM，可直接运行此次受测的完整发布命令：

```powershell
python scripts/run_regression.py --native --vocalizer --release --llvm-bin vendor/llvm-20.1.8/bin --spectre-atl-fallback --allow-external-screen-effect --jobs 2
```

需要重建本地 LLVM 提取目录时，先运行 `scripts/prepare_llvm.ps1`；它要求已安装 7-Zip，下载/校验/提取官方固定资产，不执行厂商安装程序。不同电脑已完整安装 VS Clang/ATL 时不必启用这两个适配选项：

```powershell
python scripts/run_regression.py --native --vocalizer --release
```

没有 VE 许可证的 CI/开发机可以运行 `python scripts/run_regression.py --native`；产物明确标为 CI 候选，不冒充经过 VE 声学门禁的正式交付。

`.github/workflows/regression.yml` 提供 Windows 自动化定义，固定第三方 Action 的提交 SHA、工具版本和 NVDA 提交，仅需仓库只读权限。actionlint 1.7.12 验证其语法和 Action 输入；本地完整流程已实际运行。没有替用户创建/推送远程仓库，也没有声称已在 GitHub 托管机器上实际跑过。

流程按顺序执行：源码准备 → Python/工作流静态检查 → 严格插件测试 → NVDA 编译 → 官方测试 → 原生插件链路 → 性能 → VE 两套渲染及审计 → 证据校验和可重复打包。任何失败、缺依赖、未批准的 skip 或源码/证据哈希不匹配都会中止，不能继续发布。上述单一显示环境例外必须显式选择并在最终报告保留；CI 默认不启用该例外。

有意修改生产规则/实现之后，需要明确刷新与审核派生语料，再重新跑完整流程；流程本身不在测试前自动“接受新答案”：

```powershell
python tools/generate_final_renderer_fixture.py
python tools/boundary_acoustics.py generate
```

静态期望结果仍由独立回归断言保护，声学比较采用另一枚常用同音字，不能仅靠重新生成文件掩盖丢失的纠正。`.gitattributes` 禁止 Git 静默转换换行字节，避免开发机与 CI 的文件 SHA 无故不一致。

## 6. 响应速度与声学判据的限度

本次修复没有增加扫描距离，边界检查仍为 O(1)。性能脚本覆盖无候选短句、普通命中、`盛汤$`、`$行 12|`、英文撇号和约 8 KB 的无候选/稀疏/密集/极端候选串。结果保存于 `artifacts/performance-report.json`，与实际源码及基准脚本哈希绑定。

短样例每轮 100,000 次、共 7 轮；常规长样例每轮 2,000 次，密集和极端样例每轮 50 次。数字是“每轮批量平均耗时的中位数”，不是单次 p99，不包括真实 NVDA 分发、COM/IPC、语音合成、首音、音频或取消延迟。性能门禁用于抓明显数量级退化，不等于对每台机器的零延迟承诺。

VE 回归在独立进程直接使用本机 DLL，收集 PCM/音素并保存 WAV，不播放音频。120 组新增用例的修正文本均与常用同音同调锚点产生相同的完整 PCM 和音素序列；这比仅比较不含可独立解释声调信息的私有音素 ID 更强，但仍不能推导出所有上下文、所有声音必然正确。高层驱动的额外用户词典/tuning、Word 自身分块、人耳试听仍须单独验收。
